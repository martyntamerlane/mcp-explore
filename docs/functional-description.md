# Functional Description — mcp-explore

> **Status**: redesigned 2026-08-26 per [`docs/specs/2026-08-26-luminous-deck-redesign.md`](specs/2026-08-26-luminous-deck-redesign.md) — light-first "luminous precision" identity, the control-deck stage (replacing the 2026-08-25 flow view), a scoped Run verb, and the two-door landing. This describes actual behaviour — update it in the same change as any feature work.

## Concept

A public, shareable web page. A user inputs the URL of their MCP server; the page connects directly from their browser and displays the server's tools, resources, prompts, and capabilities as an interactive graph — pleasing and simple.

## Features (built)

- **Landing — two equal doors** (`ConnectScreen`) — hero copy (including a one-line MCP gloss for newcomers) above two side-by-side doors. **Door 1 "Connect your server"**: URL input + Connect, a collapsed "Add headers" disclosure with repeatable name/value rows plus a "Remember headers on this device" opt-in, and a recent-servers list (localStorage, `mcp-explore:recents`) that only persists headers when the user opted in. **Door 2 "Explore a live demo"**: the more inviting of the two (tinted wash, lit hairline, prism motif) — "Explore the demo" connects to the built-in in-page `demo-issue-tracker` server (6 tools, 2 resources, 2 prompts) over an `InMemoryTransport`, no network involved. One ambient motion only (a slow canvas-tint drift); the deck is never previewed on the landing, so the power-on stays the first payoff.
- **Connection + diagnostics** — Streamable HTTP with automatic fallback to legacy HTTP+SSE, via the official MCP SDK; only `http:`/`https:` URLs are accepted. On failure, a **connect-error panel** names the failed transports, explains the browser CORS requirement with the exact headers to add (`Access-Control-Allow-Origin`, `Access-Control-Allow-Headers`, `Access-Control-Expose-Headers: mcp-session-id`), notes the localhost local-network permission prompt, and offers a collapsed "Technical details" dump of the raw per-transport errors.
- **The control deck** (`DeckView`, the default stage) — a hairline-bordered **server boundary** (the future multi-server seam) whose header carries the prism emblem, server name, `v{version}` chip, transport chip, and the filter box. Inside: **tools as a central grid of buttons** — entity glyph (circle), mono name, runnable state visible at a glance — and a **flanking rail** of resources and prompts as compact clickable lists. Canonical section headers with counts (`TOOLS · 6`) and 11 px glosses (*actions it can perform* / *data it exposes* / *ready-made instructions*) are retained. Sections over their preview cap (24 tools / 10 rail entries) show "+ N more" expanders; an active filter bypasses the caps and makes non-matches recede across all three kinds. **Adaptive emphasis**: servers with ≤ 4 tools get a compact centered grid and a widened rail instead of a vast empty centre. Hovering any button/entry shows a calm **anchored tooltip** (fixed below the element, never cursor-chasing) with its one-line description; a small `i` icon opens the detail panel without running. Duplicate ids are deduped (first wins). Deterministic layout; still at rest.
- **The Run verb** (scoped TODO-1 slice) — click semantics per tool class: tools hinted read-only (`readOnlyHint: true`) and runnable **run on a single click**; runnable tools without the hint use **arm-then-fire** (first click charges the button with a ~150 ms light sweep and the label becomes "Run *name* ▸"; the second click fires; Esc, clicking elsewhere, scrolling, opening the panel, or a 4 s timeout drains the light back out; exactly one tool can be armed). Tools whose schema has required arguments are **input-required**: a visually distinct face (dashed hairline, "needs input" tag, no run affordance) that opens the detail panel, which states honestly that *inputs required — running these is coming*. Eligibility: every demo-server tool, plus any tool on any server with no required arguments. While a call is in flight the button's edge light circulates; results land in the detail panel as sanitized text/pretty-printed JSON (size-capped at 50,000 chars), errors with a distinct honest treatment — no fake success motion. Full keyboard parity: Enter arms, Enter fires, Esc disarms; armed state is surfaced via `aria-pressed` and a live label change.
- **Detail panel** (`DetailPanel`) — spring-based slide with interruptible reverse (dismiss mid-flight reverses fluidly), content staggering in ~20 ms per element. Tools show a RUN section (in-flight / result / error states) above an arguments table (name, type, required marker, description, enum chips, default value) derived from the JSON Schema; types render newcomer-friendly ("text", "list of text", "true / false") with the raw protocol type beneath. Resources show URI/mime type/description with a "Load contents" button that fetches on demand and renders text (pretty-printed if JSON), images (`data:` URI), or a "binary contents" notice. Prompts show their argument list. Every entity keeps the **raw JSON disclosure ladder** — collapsed `<details>` that renders the full object with a copy button only once opened.
- **Choreography** — calm 150–250 ms baseline; expressive motion only at: the **deck power-on** (boundary settles, grid ignites in a staggered cascade, rail follows — one-shot per connect, under ~1.5 s), the arm/fire/result loop, the panel spring, expander reveals, and the landing's single ambient drift. At rest the app is still; `prefers-reduced-motion` swaps every entrance and loop for instant states (via `MotionConfig reducedMotion="user"` plus a global CSS floor).
- **App chrome** — a slim header with the prism brand mark and a Disconnect button; server identity lives in the deck boundary, not the chrome.
- **Shareable URLs** — connecting via a typed/recent URL writes `?server=<encoded url>` to the address bar with `history.replaceState`; loading that URL auto-connects. Auth headers are never persisted to the URL — only the server URL is encoded. Disconnecting clears the query string back to the bare path.

## Dune mode (easter egg)

A hidden alternate theme, originally specced in [`docs/specs/2026-08-24-dune-mode-design.md`](specs/2026-08-24-dune-mode-design.md) and visually redesigned per [`docs/specs/2026-08-26-dune-cinematic-redesign.md`](specs/2026-08-26-dune-cinematic-redesign.md). Entering the shortened Konami code (`↑↑↓↓←→` — arrows only, trimmed from the classic 10-key code on 2026-08-26) anywhere on the page toggles a full-session fluorescent teal/green reskin (persisted in `localStorage`, `mcp-explore:dune-mode`) — the landing screen, graph, and detail panel all pick up the alternate CSS tokens with no component code changes, since every color already flows through `var(--…)` custom properties. While active, the page background becomes a cinematic scene: an AI-generated planet-limb-at-sunrise image, color-graded fluorescent, kept alive by a slow perpetual camera zoom, pointer-tracking depth parallax across five layers, a deterministic seeded starfield with staggered twinkling, a breathing sun flare, drifting atmosphere haze, muted city-light clusters shimmering in the shadowed cloud band along the planet's surface, a periodic shooting star, and animated film grain. All motion is CSS/JS transforms with a `prefers-reduced-motion` fallback to a still frame. A legibility scrim sits behind the centered connect form, where the image's sun would otherwise wash out the UI. Entering the sequence again toggles it off. (The former procedural heighliner scene and the click-triggered URL-seeded ship departure were removed in the redesign; a connect animation is deferred until the still scene is settled.)

Built as a fully isolated, self-mounting module (`src/dune/`) loaded via its own Vite entry script — see Architecture Overview for the module map and isolation rationale.
